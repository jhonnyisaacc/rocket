# Memecoin Data Truth Registry

Status: current research contract, 2026-09-24. Protocol semantics require versioned decoders and raw evidence. Official [Pump program documentation](https://github.com/pump-fun/pump-public-docs/blob/main/docs/PUMP_PROGRAM_README.md) and [PumpSwap documentation](https://github.com/pump-fun/pump-public-docs/blob/main/docs/PUMP_SWAP_README.md) are current references; a historical event must use its contemporary layout.

| Field or label | Authoritative evidence | Unacceptable shortcut | Availability and version rule |
| --- | --- | --- | --- |
| Identity / creation | Confirmed Pump create instruction/event, mint and transaction/slot | Symbol or page label | Record receive time, block time, program ID, instruction order and decoder version. |
| Earliest feature availability | Raw successful `CreateEvent`/`TradeEvent` bytes in received `logsSubscribe` frame | Retroactively assigning block time as live availability | MC-001 captured frame receipt, later reconciled signatures and pinned IDL. Transaction fetch may be later; retain both clocks. |
| Curve state / liquidity | Bonding curve account or ordered state-changing events and current real/virtual reserves | Advertised market cap or static graduation reserve | State is usable only after it was observed/received; preserve curve layout and quote mint. |
| Completion | Bonding curve `complete` and reserve state (`real_token_reserves == 0` in current Pump docs) | Market-cap threshold | Distinguish completed curve from actual migration. |
| Migration / graduation | Successful migration instruction and canonical PumpSwap pool creation/state | “Graduated” API flag alone | Record migration slot and observed availability; historical version applies. |
| PumpSwap pricing/liquidity | Pool account plus base and quote token balances and quote mint | Doubling a stale quote vault or assuming WSOL | Current docs define **effective quote reserves = quote-vault balance + pool virtual_quote_reserves**. Record both, pool layout and slot. Quote vault alone is insufficient if virtual reserves are nonzero. |
| Wallet buy/sell | Signed transaction, instruction, owner balance changes, funding and fees | Token receipt or transfer alone | Distinguish fee payer, owner, routed input, deposits and refunds. |
| Holder concentration | Mint supply and beneficial holder accounts after identifying/excluding pool/vault accounts | Raw largest token account as developer holding | #30 found the largest account to be the pool base vault in 19/19 checked rows. |
| Forward executable return | Entry quote from state observable at decision plus size, fee, latency/failure; independently observed exit | Future candle midpoint or leader fill | Version execution formula and fee schedule. Failed entry is no position; failed exit retains inventory. |

MC-001 pinned Pump IDL revision `81091419e4457566469d4e2a27f64ed84d42419c` and found that its `CreateEvent` and `TradeEvent` bytes decode in the measured session. Current native non-Mayhem `TradeEvent` fee and reserve arithmetic reproduced 208 observed fills, including fee ceiling rounding. Buyback and holder-reward amounts were allocations of charged fees in those events, not extra charges. This is scoped protocol evidence, not a general promise across Mayhem, other quote mints or future upgrades.

MC-002 expanded the native non-Mayhem quote audit to 6,887 supported events. A default creator address produced a zero creator fee despite a nonzero configured `creator_fee_basis_points`, so the effective charge is a transaction fact, not the bps field alone. Six exact-input events exceeded the simple ceiling protocol fee by one lamport; this unresolved rounding boundary is tracked explicitly and must not be silently called an exact formula. One zero-cash dust sell is outside the economic quote model. Future execution tests must pin these cases and compare actual balance deltas, not just event arithmetic.

MC-003 separately reconciled 8,712 supported native non-Mayhem quotes and 3,564 adjacent state transitions. Solana transactions can log `Program data:` from multiple invoked programs; a matching event discriminator alone does not prove Pump provenance. The decoder now requires Pump to be the active program on the invocation stack. This was verified against two colliding non-Pump event records in MC-003. The economic proxy still lacks observed balance deltas, inclusion and exit-route evidence.

MC-004 uses [Solana transaction metadata](https://solana.com/docs/rpc/json-structures) to check whole-transaction `fee` and indexed pre/post token balances for a fixed sample. Fee payer net lamport change is not a trade cash delta: rent, routing and other transfers share the transaction. An account created in the same transaction has no pre-token balance, so a missing source-side delta must remain unverified rather than fabricated. Transaction version support and each RPC retrieval time are preserved; the later fetch cannot change the original event availability time.

The pinned IDL also emits explicit `CompleteEvent` and `CompletePumpAmmMigrationEvent` records. They are distinct labels: curve completion does not by itself prove a usable migrated pool, and a migration event must carry a pool address and observed availability. `TradeEvent.user` is now retained as a prospective participant identifier, but is not automatically a verified wallet buy or beneficial owner; transaction accounting remains necessary before such labels are admitted.

MC-004's later user-owner cross-check matched 47/48 single-event account owners to the event user. One routed sell emitted an intermediary address while the source token account belonged to another owner. This concrete counterexample prevents treating every distinct event user as a distinct independent buyer or seller.

MC-005 exposed additional native exact-input rounding boundaries: up to one lamport on each of protocol and creator fees, plus a curve-completing buy whose input-token approximation differed by 498 base units while the exact-output calculation matched the event. Twenty gross-zero or fee-exhausted dust sells do not support a positive-cash economic exit. The archived initial audit failed before these classifications; the corrected audit reports them explicitly and still rejects any larger discrepancy. MC-005 also had episodic 10–28-second CreateEvent timestamp-to-receipt gaps, so a block/event timestamp cannot be substituted for actual feature availability.

MC-006 repeated this timing issue with a batched disk-sync collector: 118/272 CreateEvents were more than five seconds old by the integer event timestamp at receipt, and p90 was 28.056 seconds. This is an imprecise age measure but establishes a real actionability risk. An alternate public websocket initially emitted slots 26 behind a pre-subscription `getSlot`; the audit now pages the independent index back to the earlier first notification slot. With that correction, the alternative stream missed 466/871 interior signatures and is rejected as an acquisition source. Neither provider's reported block time should be backdated into feature availability.

MC-007 found one identical, all-ones signature `logsNotification` in both official public websocket aliases. The independent program index did not contain it, later signature status was null, and transaction fetches returned null. The emitted CreateEvent is an uncorroborated notification, not a verified creation identity. Preserve the raw frame and count it against exact-coverage validation rather than silently dropping it from the launch universe. Near-identical receipt clocks on the two aliases do not supply independent acquisition proof.

MC-008 separated transaction signature coverage from event-log completeness. Its full block feed independently matched all 7,481 interior signatures, but 29 successful publicnode block-metadata records explicitly said `Log truncated`. Two same-mint reserve state gaps arose after logged multi-sell sequences were cut before their final emitted event. A later official RPC `getTransaction` check verified all 29 identities and recovered 14 additional TradeEvents from complete logs. A complete signature index cannot certify five-second trade flow when a provider truncates logs; such transaction and affected mint windows stay `UNKNOWN` at the original decision time. The later complete response may repair retrospective truth only from its own retrieval clock. The block frame's receive clock remains later than its chain block time and cannot be backdated.

MC-009 showed that a third-party `subscribeNewToken` receipt can precede an official Pump log receipt on the same signature, but its coverage and program scope differ. Its 52 signatures all resolved to successful transactions; 45 were Pump `CreateEvent`s and seven were Bonk creations. The feed missed 14/58 native Pump creations in the frozen core. Preserve `pool`, transaction program, quote mint, and both receive clocks; a provider's `txType: create` is not a sufficient Pump-program or full-universe identity. The official stream again emitted an all-ones 64-byte signature without independent transaction history, so structural signature validation and raw-frame quarantine must happen before feature admission, with the anomaly counted rather than erased.

MC-010 prospectively applied that structural rule. Its 154,216 raw notifications contained zero invalid signatures, and 154,144 valid interior signatures matched the independent chain index exactly. This validates the new rule on this window without changing MC-007/MC-009's earlier raw-feed failures. All 310 decoded creates were received within five seconds of their coarse integer event timestamp in this window; earlier burst windows still prevent a continuous fast-service claim. Later signed top-level `create_v2` inspection strictly confirmed 238/240 fast scored creations. Two compound or routed creates lacked that exact top-level instruction pattern, so they remain unresolved for this cohort rather than borrowing the event mint as signed instruction identity. The MC-010 evidence archive SHA-256 is `704a48905b3dd0fb993f7dd44775d5642faa5da4a6cdf647f8e5199c59c924e7`.

MC-011 selected 144 single-event early trades without consulting outcomes and fetched their signed transactions after the fact. Unique event-sized token-account owners were visible for 142, and all 142 matched `TradeEvent.user`; two buys had no matching positive owner balance delta. Forty-four trades entered Pump through another top-level program, so route classification must survive even when the emitted user and token owner agree. MC-004's separate routed-sell mismatch still forbids a universal event-user identity assumption. A token-account owner, signer and fee payer can differ; none alone proves independent beneficial control or funds paid to a trade. Preserve ambiguity and fetch clocks. The MC-011 evidence archive SHA-256 is `edd82a6033411784383b223913076fc046c1dd18fede758bc07d76f9cffd6c06`.

MC-012 saved later DEX Screener pool listings for 54 curve-unavailable and 54 quoted MC-010 names. All unavailable names had only a `pumpfun` listing at retrieval, and one control's PumpSwap listing was created after its frozen 67-second exit clock. An API listing is a discovery hint with its own receive time; it is not an on-chain reserve snapshot, size-aware quote or proof of a venue's absence at an earlier clock. Preserve pair address, DEX label, mint match, listed creation timestamp and request/receive clocks, and require direct chain/route verification before changing any exit label. Archive SHA-256 is `a282cd5aa83fdc6d9e17b6621bd58ba84ca22f67f1874dc09463f7f91c04c6b2`.

MC-013 saved time-stamped, confirmed `getMultipleAccounts` responses for every decoded creation's emitted Pump bonding-curve address at receipt +7/+67 seconds. Require the Pump owner, pinned `BondingCurve` discriminator/layout, response `context.slot` at or after creation and no later-than-visible same-mint trade, and the actual dispatch/response clocks before treating the account as an as-of quote state. All 550 scheduled reads in this panel decoded and met timing bounds, but five context slots preceded an already visible trade; one scored case stayed unknown. Account reserve equality to the latest visible event occurred in 431/550 reads. A later signed `getTransaction` identity confirms a creation retrospectively and keeps its later retrieval clock; it is not an early feature. The direct-account quote still lacks achieved inclusion, fill and alternate-route proof. Archive SHA-256 is `f187c704021946e4bc5453e69d0d80f76f08f11e868b1ef7bf3cd518a40f41b7`.

MC-014 prospectively retrieved `getTransaction` metadata for a bounded first-three successful early-buy signature sample. All 135 selected buys in 61 native non-Mayhem core launches had a unique event-sized positive token-account owner in a signed, successful same-signature/same-slot transaction **by the creation receipt +5-second checkpoint**. Preserve the request and response clocks, null/error attempts, event mint/amount/user, token-account owner, signer, fee payer and top-level route separately. Owner, signer and payer matched in this selected sample, including eight routed top-level transactions, but address agreement is not proof of independent beneficial funding or control. Other buys, other windows and earlier feed-delay bursts remain unverified. Archive SHA-256 is `c7bb3e6bd726b9597616797d9783751b3a1c175a134251f77b9deafe1cd8ac0b`.

MC-015 repeated the signed-owner and direct-account acquisition on a ten-minute cohort. The independent index matched 127,995/127,995 interior signatures; 532/532 Pump account responses were timely and decodable. Among 401 selected early buys, 390 had unique token-owner truth by the creation +5-second checkpoint, ten successful responses arrived later and one owner was ambiguous. Those eleven cannot be converted into a zero-valued buyer feature. Later signed top-level creation checks resolved 146/152 scored names and left six compound/routed names unresolved; their later retrieval must not be backdated. The frozen buyer-size rank failed its costed direct-account economic gate. Selected buyers' whole-transaction fees also varied widely (113/401 above 1,000,000 lamports), so a fixed modeled per-leg fee is a scenario, not a proven Rocket execution cost. Archive SHA-256 `0a2ac1f6745271b3a00dad7cd331bb05f86588f3e41efb590de85553ddf47e8e`.

MC-016 distinguishes a signed transaction's fee payer from the token-account owner and from a beneficial funding source. Among 123 MC-015 creations with at least two timely distinct selected owners, no different owners shared a fee payer, but this only rules out that directly visible payer overlap in this sample. Forty-three payers appeared across multiple creations. Prior transfers or off-chain control were not traced, so funding-source and beneficial-controller labels remain unknown. The [deterministic report](data/mc016-payer-overlap-20260924.json) replays from the MC-015 archive.
