# MC-011 frozen design — early trade actor and route truth calibration

Parent MC-010. This is a retrospective **mechanism and data-quality calibration** on the already observed MC-010 panel, not an independent strategy holdout and not a return-rank test. The question is whether a received Pump `TradeEvent.user` can safely stand for the owner of the traded token account in the five-second feature window, and how often the trade is directly invoked versus routed. MC-004 found one routed-sell counterexample among 48 single-event transactions. A mismatch, ambiguous balance attribution, unavailable transaction or fee-payer difference must be reported, never silently assigned to the event user.

Before fetching any MC-011 transaction, select only MC-010's 238 strictly create-verified fast scored mints. Reconstruct their original five-second feature window from the create frame's `available_at` through `available_at + 5 seconds`, inclusive, using *trade frame receipt* clocks. Group the unchanged MC-010 top quartile within each chronological split versus the rest; this group is used only to stratify mechanism calibration. Keep only a signature with exactly one decoded Pump `TradeEvent` in the full observed panel so an event-sized token balance movement can be attributed. Preserve counts for all eligible early events and excluded multi-event signatures. Form four strata: top buy, rest buy, top sell, rest sell. Sort signatures within each stratum by `(SHA256('mc011:' + signature), signature)` and take 48, 48, 24 and 24 respectively, or all if a stratum is smaller. Do not inspect outcomes when sampling. Freeze selection JSON, source hashes and the implementation before the RPC reads.

Fetch each selected signature's `getTransaction` at `confirmed` from the independent publicnode RPC with `jsonParsed` and supported version 1. Save every response/failed attempt, request and receive clock, status and hash. Use paced bounded retries; an unavailable response remains `UNKNOWN`. Require transaction signature, slot and success to match the observed trade before reading metadata. For the event's mint, calculate signed pre/post token balances by `accountIndex`. A unique account whose change equals the event `token_amount` (+ buy, − sell) supplies its recorded token-account owner. Multiple or no matching accounts are ambiguous. Compare that owner to `TradeEvent.user`, fee payer and signer keys; classify top-level Pump invocation versus routed top-level program. Report whole-transaction fees, but do not assign all fee-payer lamport movements to the trade or call an account owner a beneficial controller.

Report selection and response coverage, all ambiguity classes, per-stratum owner match/mismatch counts and exact 95% intervals, top-level versus routed counts, fee-payer/owner and signer/owner agreement, and fee distributions. A mismatch in either buy or sell stratum falsifies the universal event-user-as-owner shortcut; zero sampled mismatches bounds rather than proves it. The result may motivate a **new** early actor feature on a later, separately frozen prospective panel only if identity is point-in-time obtainable. It cannot change MC-010's frozen score, negative economic conclusion or Rocket decision state. No signer, wallet or order submission is involved.
