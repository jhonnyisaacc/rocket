# MC-014 result — signed early-buyer ownership by five seconds

Status: **accepted as a bounded point-in-time signed-identity acquisition calibration**, not a buyer-independence or economic-entry result. The [frozen design](MC-014-FROZEN.md) and read-only tools were committed as `d024cb2` before this fresh 180-second panel.

The Solana Labs `confirmed` Pump subscription ran from acknowledgment at 2026-09-24 17:54:37.887 UTC through 17:57:37.913 UTC. It saved 48,473 notifications and 48,474 raw frames with no collector error. The independent publicnode index matched **48,270/48,270** valid signatures in fully observed interior slots: zero missing/extra or structural quarantines. There were zero truncated successful logs, decoder errors, supported native state failures or material quote failures. The pinned IDL decoded 90 creates and 10,704 trades. All 90 create receipts met the coarse five-second chain timestamp screen (median 1.336 seconds, p90 2.049, maximum 3.787), which is not precise network latency.

The concurrent companion parsed every frame, decoded the same 90 creations, selected the first at most three distinct buy transaction signatures within each native non-Mayhem creation's receipt +5-second window, and saved responses for all **135** selected buys. The selected events, signatures, mints, slots, source hashes and receipt clocks exactly matched the separately audited stream. All 135 `getTransaction` responses succeeded on the first attempt. The core contained 61 native non-Mayhem creations; all 61 had at least one selected buy. All **135/135** selected buys had a successful signed transaction and a unique event-sized positive token-account owner available by the creation's five-second checkpoint. Every one of the **61/61** creations had all of its selected owners verified by that clock, passing both frozen 80% availability screens and the 30-create minimum. Event receipt to signed response lag had median 0.419 seconds and p90 0.900; creation receipt to signed owner had median 0.485 seconds, p90 1.573 and maximum 4.657. The companion started about eight seconds after the primary collector, so the earliest requests include its startup catch-up; no response in this panel crossed its own creation checkpoint.

All 135 identified token owners matched the emitted `TradeEvent.user`; all were transaction signers and fee payers in these selected buys. Eight transactions entered Pump through another top-level program. This is direct signed **token-owner** evidence for this selected, bounded population. It does not identify beneficial controllers, establish independence across apparently distinct wallets, or validate event-user semantics for every trade and regime. MC-004's routed-sell counterexample and MC-011's two ambiguous buys still apply.

The selected transactions' **whole-transaction** network fees had median 34,161 lamports, p90 1,335,000 and maximum 340,005,000; 48/135 exceeded 155,000 and 33/135 exceeded 1,000,000 lamports. These are observed buyers' transaction fees, not costs that Rocket would necessarily pay. They show that neither fixed fee scenario uniformly bounds the observed sample, so a favorable modeled return would still require prospective inclusion and priority-fee evidence.

There were 21 launches with one selected buy, six with two and 34 with three. Within each launch, all selected token-owner addresses were distinct. Thus a proposed feature that merely counts distinct owners among these first three buys would equal the capped buy count on this panel; it is not a demonstrated incremental risk or return signal. No returns from this calibration window were used to choose a threshold. A later full feature test should prespecify an actual economic mechanism, such as the distribution of signed buyer sizes, and compare it with the unchanged simple flow baseline on a fresh temporal holdout. It also needs route-aware exit state and realistic inclusion costs before any entry promotion.
