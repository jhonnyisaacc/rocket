# MC-014 frozen design — five-second signed buyer availability calibration

Parent MC-011/MC-013. The current log feed provides `TradeEvent.user` promptly in some windows, and MC-011's later signed-transaction sample usually matched that address to an event-sized token-account owner. That later check cannot establish what signed identity was available by a five-second decision. MC-014 tests **acquisition and identity availability**, not economic alpha or a new entry rule.

Collect a fresh, bounded 180-second Solana Labs Pump `confirmed` `logsSubscribe` panel with the pinged Python collector, maximum 256 MiB raw. Start a concurrent read-only publicnode companion with a 240-second hard deadline, maximum 32 MiB saved responses and 400 selected transaction signatures. Parse all raw frames with the same pinned IDL and Pump invocation stack. Retain every creation and its frame-receipt clock. For every native, non-Mayhem creation, select the first **three distinct successful buy transaction signatures** whose `TradeEvent` frame arrives from create receipt through create receipt +5 seconds, sorted by frame receipt then signature. Launch `getTransaction` with `jsonParsed`, `confirmed`, transaction version 1 as soon as each selected buy is seen, at most eight requests concurrently. Save every selected event, dispatch/response clock, HTTP/error/body and exact RPC source; make at most three attempts per signature, with 0.5- and 1-second retry delays after unsuccessful attempts. Do not query a fourth buy for a mint. A call that completes after the creation's five-second checkpoint is saved but unavailable at the decision. No later retry may be backdated. Keep all created names and all selected failed/late requests in the denominator.

Independently reconcile the primary raw stream against the publicnode signature index with the preexisting structural quarantine rule. Require exact valid interior signature coverage, zero successful-log truncation, event decoder failure, supported native state failure or material quote failure. Compare the companion's selected create/buy signature, mint, slot and event source hash to the independently decoded stream; any discrepancy fails the acquisition gate. Parse a successful signed transaction only if signature/slot match, transaction is successful and a **unique** event-sized positive token-account delta owner exists by the saved response clock. Preserve `TradeEvent.user`, token owner, signer set, fee payer, top-level route and ambiguities separately. One owner, signer or payer address is not proof of one beneficial controller.

Primary metrics: fraction of selected buys with verified unique owners available no later than each creation's receipt +5 seconds; fraction of native non-Mayhem creates for which *every selected first-three buy* is so verified, including zero-buy creates as a separately reported stratum; request/response latency; null/rate-limit/ambiguous/mismatch counts; and create receipt-age distribution. Minimum useful availability gate: at least 80% of selected buys and at least 80% of native non-Mayhem creates with at least one selected buy have all selected owners verified by the decision clock, with at least 30 such creations in the covered core. The gate is about this source's availability, not causal buyer independence. A later signed response may calibrate retrospective truth but does not count toward these thresholds.

If the 180-second calibration fails these thresholds, do not invent a verified-buyer five-second feature on the already observed panel. Diagnose whether latency, null responses, rate limiting, routing or ambiguous token accounting caused the failure, and test another source or clock before a frozen economic holdout. If it passes, freeze a separate full prospective actor feature and costed outcome experiment before collecting that cohort; do not tune on MC-014's returns. No `ENTER`, live signer, order or scheduler is authorized here.
