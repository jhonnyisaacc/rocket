# MC-004 frozen design — transaction accounting calibration

Parent: MC-003. Frozen before transaction responses for the cohort sample are fetched. This is a protocol and execution-cost validation, not a feature search or entry-rule test. Source population is every decoded, native-SOL, non-Mayhem `TradeEvent` in the archived MC-003 prospective stream. Exclude zero-cash dust trades from fee/amount arithmetic but retain their count. The observation clock remains the original WebSocket frame receipt; this later RPC fetch cannot create an early feature.

Group events by transaction signature. Select 24 signatures with exactly one supported buy event, 24 with exactly one supported sell event, and eight signatures with multiple supported trade events. Within each stratum, sort signatures by SHA-256 of `mc004:` plus signature and take the first requested count. Record each stratum's full population and any shortfall. Preserve the raw `getTransaction` JSON response, request/retrieval times, endpoint host, HTTP/RPC errors and a SHA-256 digest for every selected signature. Use `jsonParsed` and `confirmed`. Do not substitute a different signature after a failed fetch.

Transport amendment before analysis: the initial request declared `maxSupportedTransactionVersion: 0`; a selected signature returned RPC error `-32015` stating it uses transaction version 1. Preserve that failed response, retry the **same fixed signatures** with `maxSupportedTransactionVersion: 1`, and record each attempt. No population, stratum, outcome, cost or accounting rule changes.

For each successful response verify signature, slot and transaction success against the streamed observation. Record `meta.fee` as an actual network fee for the **whole transaction**, with its fee payer; report fee distributions separately for single-buy, single-sell and multi-event strata. Record top-level Pump versus routed invocation, token account creation/closure, number of Pump trade events and whether non-Pump transfers occur. Compare the event token amount to the change in the curve token account and recipient/source token account when a unique account can be identified from transaction balances and inner instructions. Compare event SOL amount and charged fees to changes in the curve/fee accounts only where attribution is unique. Mark routed, multi-event, rent and unrelated transfer cases `AMBIGUOUS`; never force fee-payer net balance change to equal trade cash.

Report coverage, unavailable transaction responses, mismatches, ambiguities and fee distribution. A mismatch in an unambiguous direct trade challenges the quote model and blocks economic interpretation until explained. Do not retune MC-002/MC-003 costs after seeing these results; use measured costs to predeclare a new independent experiment. The next strategy experiment still requires fresh covered windows and survival/risk features, not reuse of these calibration transactions as a held-out cohort.
